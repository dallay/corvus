## Advanced Authentication

Some providers support advanced authentication methods beyond simple API keys:

### OAuth & CLI Authentication

- **Google Gemini**: Corvus can automatically reuse credentials from the Gemini CLI. If you have run `gemini` and authenticated, Corvus will find your OAuth tokens in `~/.gemini/oauth_creds.json`.
- **OpenAI Codex**: Uses an OAuth-based flow for authentication.
- **GitHub Copilot**: Reuses your GitHub CLI authentication or environment-provided tokens.

### Setup Tokens

For **Anthropic**, you can use an `ANTHROPIC_OAUTH_TOKEN` (setup token) as an alternative to a standard API key.

## Regional & Specialized Providers

Corvus also supports several regional and specialized providers, particularly for the Chinese market:

- **Moonshot (Kimi)**: `moonshot`, `moonshot-intl` (`MOONSHOT_API_KEY`)
- **GLM (Zhipu)**: `glm`, `glm-cn` (`GLM_API_KEY`)
- **MiniMax**: `minimax`, `minimax-cn` (`MINIMAX_API_KEY`)
- **Qwen (DashScope)**: `qwen`, `qwen-intl`, `qwen-us` (`DASHSCOPE_API_KEY`)
- **Qianfan (Baidu)**: `qianfan` (`QIANFAN_API_KEY`)
- **Z.AI**: `zai`, `zai-cn` (`ZAI_API_KEY`)

## Custom Endpoints

If you have a self-hosted or OpenAI/Anthropic-compatible API, you can use a custom provider string:

- **OpenAI-compatible**: Use `custom:<URL>` as the provider name.
- **Anthropic-compatible**: Use `anthropic-custom:<URL>` as the provider name.

Example:
```bash
corvus onboard --provider "custom:http://localhost:1234/v1" --api-key "your-key"
```

## Credential Resolution

Corvus resolves credentials in the following order:

1. Explicitly provided `api_key` in `config.toml`.
2. Provider-specific environment variable (e.g., `ANTHROPIC_API_KEY`).
3. Generic fallback environment variables (`CORVUS_API_KEY` or `API_KEY`).

## Provider Pools (Reusable)

Account pools are provider-agnostic: the pool wrapper applies to any provider
registered in the provider factory. Configure pools under
`reliability.account_pools.<provider>` and the runtime will select an account
per request while keeping providers cached per account. This means new or
custom providers automatically inherit pooling behavior once they are wired
into the provider factory.
